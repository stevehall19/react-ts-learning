**The race E1 found.** The first e2e run failed with HTTP 500: Playwright's two quick increment clicks ran concurrently, both read the row, and MariaDB 11.8 (`REPEATABLE-READ` with `innodb_snapshot_isolation=ON`) rejected the second update with error 1020 ("Record has changed since last read"). Other databases would have lost an increment silently. The learner reproduced it with `concurrentIncrementsAreNotLost` (20 increments on 10 threads via `invokeAll`, red first), then fixed it with a pessimistic lock: `findByIdForUpdate` (`@Lock(PESSIMISTIC_WRITE)`, i.e. `SELECT … FOR UPDATE`) used by `increment` and `reset` through `CounterService.findForUpdate`. Optimistic locking (409s) and an atomic `UPDATE` were discussed and rejected.

**A10, idempotency.** Started from the learner's question "what's the best way to handle idempotency with Spring Boot?". Claude scaffolded the aspect, annotation, migration and exception (checked against a reference solution first); the learner wrote the tests (red first), the controller changes, the handlers, the cleanup job, the repository refactor and the OpenAPI docs. How it works: the client sends an optional `Idempotency-Key`; `IdempotencyAspect` runs one transaction that `INSERT`s the key (`IdempotencyKeyRepository.claim`), proceeds, and stores the status, `Location` and body. A concurrent same-key request blocks on the primary key until that commits, then gets `DuplicateKeyException` and replays the stored response (`Idempotent-Replayed: true`). The same key with a different request hash gets 422. A failure rolls the key back with everything else, so errors aren't cached. Endpoints must return `ResponseEntity` (the aspect casts). Only create and increment are `@Idempotent`; reset and delete are naturally idempotent. Design choices the learner accepted: `JdbcClient` rather than JPA for the key table (immediate `INSERT`, specific `DuplicateKeyException`, set-based `DELETE`), a repository but no separate service yet, an optional header, and keys kept at least 24 hours by an hourly job (`IdempotencyKeyCleanup`, which logs the count).

**S1, threat model and hardening.** The learner wrote the first `SECURITY.md` draft; Claude reviewed it and, at the learner's request, rewrote it into a table (entry point, STRIDE, threat, protected today by, fix) and kept it updated with evidence. Probes against the running cluster found: integer overflow (an increment past `Integer.MAX_VALUE` stored a negative count with a 200), MariaDB's `LoadBalancer` Service exposing 3306, unhandled exceptions returning Boot's default error JSON after a 30-second Hikari wait with the database down, and the pod staying Ready without a database. Confirmed already safe: Actuator exposes only `health` by default, bad UUIDs and malformed JSON give 400 `ProblemDetail`s, and the aspect rejects `Idempotency-Key`s over 64 characters (reset and delete ignore the header). Replaying a key after its counter was deleted still returns the stored 201; that is correct, but it is the cross-user leak S3 must close. Fixes, all red-first: `dfeb484` (`Math.addExact` → `CounterOverflowException` → 422, documented with OpenAPI examples), `8d12cb5` (explicit Actuator exposure; `application-prod.yaml` turns off springdoc, the chart sets `SPRING_PROFILES_ACTIVE` from `spring.profiles.active`, default `prod`; on the branch, `KEYCLOAK_ISSUER_URI`, `KEYCLOAK_JWK_SET_URI` (`http://keycloak:8180/...`, the Service port) and `KEYCLOAK_AUDIENCE` from `keycloak.*` values), `8674a27` (catch-all handler: fixed detail "An unexpected error occurred", `log.error` with the exception). Security headers were deliberately left for S2, where Spring Security adds them.

**S2a, Keycloak.** Learner choices: their own chart (Bitnami's Keycloak is now paid; 26.8.0 was the newest tag on quay), dev mode with the realm re-imported on every start, and real tokens for the tests. The realm `counters` has the public client `counters-e2e` (password grant only, no browser login) with an `oidc-audience-mapper` adding `aud: counters-api` (added in S2b), and the test users `alice` and `bob` (passwords committed, `SECURITY.md` row 18). `KC_HOSTNAME=http://localhost:8180` makes `iss` `http://localhost:8180/realms/counters` (no trailing slash) whether a token is requested through localhost or the in-cluster Service; tokens last 300 s. **S2b, resource server** (branch `s2b-resource-server`). Done in five steps: dependencies (Boot 4 names `spring-boot-starter-security-oauth2-resource-server` and `-test`), `jwt()` on every test request plus `SecurityIntegrationTests` (401 `ProblemDetail` asking for Bearer, POST without token is 401 not CSRF 403, health guard), `SecurityConfig` + `ProblemDetailAuthenticationEntryPoint`, audience and cluster wiring, then real-token checks against the cluster: POST works without CSRF, tampered signature or payload, expired token and a no-audience token (temporary `counters-other` client, removed) all give 401 with a specific `error_description`; Bob can still change Alice's counter (row 2, S3). Claude checked every step in a scratch copy first, and found two of its own claims wrong that way (see below). Both mutation checks (remove health `permitAll`, re-enable CSRF) turned exactly one test red.

Two real bugs in Claude's scaffold were found by the learner's concurrent tests: (1) when the key holder **rolls back**, the waiting `INSERT`s deadlock each other (InnoDB shared locks on the duplicate key); (2) Claude's first fix, a 5-attempt retry loop, was flaky on CI because every round's winner also failed, so the number of rounds grows with the number of waiters (it failed every time with 30 threads). Final fix: `CannotAcquireLockException` → `IdempotentRequestInProgressException` → **409**, and the client retries, which is what the IETF draft and Stripe do. The concurrent-404 test uses 30 threads and asserts every status is 404 or 409 and at least one is 404.

## Learner profile and teaching approach

The learner is a working Java developer (Spring is familiar) using IntelliJ on Windows with PowerShell. They now also own the backend, Kubernetes and CI side.

**What has worked**

- Short lesson, then an exercise the learner writes; hints before answers. At genuine difficulty jumps (the API client in A6b), giving the core piece in full (`ApiError` + `request`) and leaving the rest worked well; the learner said so explicitly.
- Java analogies throughout: `@WebMvcTest` ↔ mocked-fetch tests, `vi.mock` ↔ Mockito, contract type ↔ interface, `@Configuration` ↔ choosing the hook at module level.
- Reviewing by reading the diff, running the checks, and exercising the real thing (curl against Spring, the browser pane against the dev server, `kubectl exec` against MariaDB, `gh run view` for CI).
- "Would this test fail if I broke the code?" — the A8 tests and the first concurrency test needed this question; the learner runs mutation checks and red-first tests when asked.
- Reading failure evidence before guessing: Playwright's `error-context.md` page snapshot showed the `HTTP 500` alert, and `kubectl logs` gave the MariaDB error. That turned a "can't find the value" question into a real backend bug.
- The learner drives design: they chose Helm over compose, Jib, an OpenAPI contract, and pushed back on `@Transactional` tests. Take these seriously and adjust the plan.

**Things to keep in mind**

- Verify before claiming. Wrong claims this track: `getResource("/")` for the module path (returned a jar), "IntelliJ runs tests from the module folder", a `--repeat` flag for Vitest, an outline in a YAML code block that the learner pasted as real YAML, Boot needing the probes property locally, and a `+7` button name (the buttons are `aria-label`ed `Increment <label>`; read `Counter.tsx` before giving locator hints). The frontend CI was also red for six commits (Prettier on Helm templates) before anyone noticed: check `gh run list` after pushes.
- The learner pastes snippets verbatim; examples must be complete and valid.
- They sometimes say "committed" or "pushed" before it has happened; check `git status` / `git log` rather than assuming.
- Leftover copy-paste from neighbouring code is the most common bug source (selectors, ids, annotations, test names). A10 alone had six cases. In S1 it showed up in OpenAPI examples (old text, placeholders) and Postman leftovers (`"Sevens"` labels).
- **Red for the wrong reason** came up repeatedly in A10: tests that were red but could never pass (no header, identical bodies), and a snapshot "failure" that was really a context-startup error. Ask "what would make this pass?" and read the failure message (`Wrote …` vs `out of date` vs `ApplicationContext failure threshold exceeded`).
- Claude's own scaffold had bugs that only concurrency on a slower CI runner exposed. Prove fixes with a stress run (more threads, repeated runs), not one green run, and check suggested test code against a scratch copy before handing it over (done for the Lesson 14 retry test).
- The learner is sometimes unsure of their own code and asks for another look. In Lesson 14, a missing `await` and a discarded return value survived two read-throughs; push for the red-first test rather than another review.
- **Run the test yourself before agreeing it's green or red.** In S1 the learner reported the catch-all test as green while it was failing on the leak assertion, and reported a commit as pushed when only one file was staged. Predict-then-probe works well: the learner's wrong predictions (a 500 on overflow, a key they thought was over 64) were the most instructive moments.
- Claude's own S1 slips: said Actuator was "open" (only `health` is exposed by default) before checking, and a probe with a 65-character key reset a real seeded counter. Probe with throwaway data, and delete what you create.
- Claude's S2 slips, both caught by checking in a scratch copy before the next write-up: it agreed the health probes would fail under Boot's default security (Boot leaves health open), and said a POST with a JWT would still get CSRF's 403 (`jwt()` skips CSRF). It also misread a rendered `keycloak-config` name as hard-coded when the template used the helper: review the template, not just `helm template` output.
- The learner asked Claude to write the PowerShell (token script, tampered tokens) rather than learn it: keep PowerShell out of the exercises and give tested, ready-to-run commands. Tested commands paste cleanly; untested ones with quoting didn't.
- Settings that tests can't see (`issuer-uri`, `jwk-set-uri`, `audiences`, and anything `jwt()` bypasses) were wrong three times before the real-token check. Check URLs against the running server, and always finish with real requests.

## Environment gotchas

- **PowerShell 5.1:** mangles `"` nested inside arguments to native programs (SQL, JSON); pipe the text on stdin instead (`… | kubectl exec -i …`, `… | curl.exe --data-binary '@-' …`). `curl` is an alias for `Invoke-WebRequest`; use `curl.exe`.
- **Line endings:** IntelliJ created some files with CRLF; Prettier then fails `npm run check`. `npm run format` fixes it; set IntelliJ's default line separator to LF. That setting only affects **new** files: IntelliJ keeps an existing file's separator (change one from the status bar, bottom right, or a whole folder with File → File Properties → Line Separators). Prettier ignores `backend/`, so CRLF in Java files isn't caught; `.gitattributes` (`* text=auto eol=lf`) normalizes on commit, and `git ls-files --eol` shows the working copy (`w/crlf`) versus the index.
- **`mvnw` executable bit:** Windows commits it as `100644`; it needed `git update-index --chmod=+x` for the Linux runner.
- **IntelliJ auto-imports:** watch for the wrong `assertEquals`/`fail` (Spring, AssertJ) and stray static imports like `AbstractPersistable_.id`.
- **MariaDB date arithmetic:** `NOW() - ?` with a number does integer arithmetic on `20261007163955`-style values and silently compares wrongly; always write `NOW() - INTERVAL ? SECOND`.
- **Spring test context failures:** if one `@SpringBootTest` class can't start the context, later classes only report `ApplicationContext failure threshold (1) exceeded`; the real cause is the first `Caused by` in the first failing class. Two `@ExceptionHandler`s for the same exception are one such cause (`Ambiguous @ExceptionHandler method`).
- **IntelliJ test runs** don't write surefire reports; ask the learner to paste the results, or run `.\mvnw test` and read `target/surefire-reports`.
- **Flyway on MariaDB:** a failed migration leaves a `success = 0` row; drop `counter` and `flyway_schema_history` (or `flyway repair`) before retrying. Never edit an applied migration.
- **MariaDB passwords:** only applied on first init of the PVC; `helm upgrade` won't change them.
- **Jib images in the cluster:** `jib:dockerBuild` loads into Docker Desktop's engine, which the kubeadm cluster uses directly. A rebuild with the same tag needs `kubectl rollout restart deployment counters-api`. Port 8080 is held by `wslrelay` (the cluster's LoadBalancer) while the API pod runs, so `spring-boot:run` can't start at the same time.
- **Spring Boot 4.1 probes:** liveness/readiness groups are on by default even outside Kubernetes; `management.endpoint.health.probes.enabled` (top-level `management:`, not under `spring:`) is set anyway for clarity.
- **`helm create` scaffolds:** removing values the templates still read (`autoscaling.enabled`) gives a nil-pointer render error; `with` blocks tolerate missing values, `if not .Values.x.y` doesn't. `helm lint` doesn't validate fields; use `helm template … | kubectl apply --dry-run=server -f -`.
- **kind vs Docker Desktop:** kind can't see the runner's Docker images until `kind load docker-image`, and its LoadBalancer services stay `<pending>`, hence the port-forward. Use `kubectl rollout status` rather than `helm install --wait`, which may wait on the LoadBalancer address.
- **Stuck GitHub runs:** a run can sit in `queued` with no jobs; cancel and force-cancel return 409, delete returns 403. Leave it (GitHub expires it), and start a fresh run with `gh workflow run e2e.yml` or an empty commit.
- **Prettier checks `.github/`:** it rewrites `[ main ]` to `[main]`; run `npm run check` before committing workflow changes.
- **Local e2e and seed data:** the seeded-counters test fails if a seeded counter was deleted from the long-lived local database; re-add it. CI's database is always fresh.
- **Spring not running:** the dev app shows "Couldn't load counters: HTTP 502" (Vite proxy's plain-text 502). In dev, React Strict Mode makes two `GET /api/counters` requests on load; that's expected.
- **Browser pane:** has its own localStorage and can drive `localhost` dev servers; useful for importing `/src/countersApi.ts` in the console to exercise the client.
