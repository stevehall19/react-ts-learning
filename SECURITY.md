# Security

Threat model for the counters app (API + MariaDB in the local cluster), written in lesson S1. Each row names an entry point, the STRIDE category, what protects it today, and the lesson that fixes it (or why it is accepted).

STRIDE: **S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service, **E**levation of privilege.

## Threats

| #   | Entry point                                       | STRIDE | Threat                                                                                                                                                                                                                                                     | Protected today by                                                                                                                                                                                                                                                                 | Fix                                                                                                               |
| --- | ------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1   | Every endpoint                                    | S      | No authentication: the API can't tell who is calling, so anyone who can reach port 8080 is accepted                                                                                                                                                        | Nothing                                                                                                                                                                                                                                                                            | S2: Spring Security resource server, JWTs from Keycloak                                                           |
| 2   | Create, increment, reset, delete                  | T / E  | Any caller can change or delete any counter; there is no owner and no authorization check                                                                                                                                                                  | Nothing                                                                                                                                                                                                                                                                            | S3: `owner_id`, owner-scoped queries                                                                              |
| 3   | `GET /api/counters`, `GET /api/counters/{id}`     | I      | Once counters belong to users, one user could read another's counter (by id or in the list). Not a threat yet: counters aren't secret today                                                                                                                | n/a                                                                                                                                                                                                                                                                                | S3: owner-scoped queries; 404 rather than 403 so ids of other users' counters aren't confirmed                    |
| 4   | `Idempotency-Key` on create and increment         | I      | Keys are global, not per user: sending someone else's key replays their stored response body. a replay can return a body for something that no longer exists                                                                                               | Request-hash check (a different body gets 422), but a matching body still replays                                                                                                                                                                                                  | S3: scope keys by user, red-first replay test                                                                     |
| 5   | Increment                                         | T      | Integer overflow: Java `int` addition wraps silently, so an increment past `Integer.MAX_VALUE` stored a negative count and returned 200 (e.g. `start: 10`, `step: 2147483647` → `count: -2147483639` on the first increment)                               | Fixed in S1. `@Min(1)` on `step` and `CHECK (step > 0)`; `Counter.increment()` uses `Math.addExact` and throws `CounterOverflowException`, which `ApiExceptionHandler` maps to a 422 `ProblemDetail`; the transaction rolls back, so the stored count is unchanged                 | Done: `Math.addExact` → `CounterOverflowException` → 422 (documented in `openapi.yaml`). `@Max` bounds not needed |
| 6   | Create, increment, reset, delete                  | R      | No record of who changed what                                                                                                                                                                                                                              | Nothing (no audit columns, no request logging)                                                                                                                                                                                                                                     | Decide: `@CreatedBy`/`@LastModifiedBy` from the JWT principal in S3, or accept                                    |
| 7   | Any endpoint that fails unexpectedly              | I      | Unhandled exceptions (e.g. the database is down) bypassed `ApiExceptionHandler` and returned Boot's default error JSON instead of a `ProblemDetail`, so the client could only show `HTTP 500`                                                              | Fixed in S1. A catch-all `@ExceptionHandler(Exception.class)` (`handleUnexpected`) returns a 500 `ProblemDetail` with the fixed detail "An unexpected error occurred" and logs the full exception on the server. More specific handlers (400, 404, 409, 422) still take precedence | Done. Covered by `CounterControllerTest.unexpectedExceptionReturns500ProblemWithoutMessage`                       |
| 8   | Port 3306, MariaDB Service (`type: LoadBalancer`) | I / T  | The database is reachable from outside the cluster; anyone who gets the password has full read/write access                                                                                                                                                | `counters` user password (git-ignored `values.local.yaml`, `secretKeyRef`)                                                                                                                                                                                                         | S6: ClusterIP; `kubectl port-forward` when direct access is needed                                                |
| 9   | Port 8080, API Service (`type: LoadBalancer`)     | S / T  | Same exposure for the API; combined with row 1, anyone who can reach the port can change data                                                                                                                                                              | Nothing                                                                                                                                                                                                                                                                            | S6: ClusterIP behind an ingress; S2 for authentication                                                            |
| 10  | Swagger UI, `/v3/api-docs`                        | I / T  | The spec itself is public anyway (`openapi.yaml` is in a public repo); the real risk is "Try it out" sending live requests to a production API                                                                                                             | Fixed in S1. `application-prod.yaml` sets `springdoc.api-docs.enabled` and `springdoc.swagger-ui.enabled` to `false`; the Helm chart sets `SPRING_PROFILES_ACTIVE` from `spring.profiles.active` (default `prod`). Local runs and tests keep the docs                              | Done (`8d12cb5`). Override with `--set spring.profiles.active=dev` to get Swagger in the cluster                  |
| 11  | `/actuator/*`                                     | I      | Endpoints like `env` or `heapdump` would leak configuration and secrets if exposed                                                                                                                                                                         | Fixed in S1. `management.endpoints.web.exposure.include: "health"` is set explicitly in `application.yaml`, so only `health` is exposed and the default can no longer drift                                                                                                        | Done (`8d12cb5`)                                                                                                  |
| 12  | `Idempotency-Key` on create and increment         | D      | Each unique key stores a row with the whole response body for at least 24 hours; nothing limits keys or counters per client, so storage grows without bound                                                                                                | Hourly cleanup job (removes old rows only; batching its `DELETE` is secondary)                                                                                                                                                                                                     | Decide: rate limiting (not in the plan yet), or accept as local only                                              |
| 13  | `Idempotency-Key` header                          | D / I  | `idem_key` is `VARCHAR(64)`: a longer key could fail at the database instead of being rejected cleanly                                                                                                                                                     | Probed. `IdempotencyAspect` rejects blank or over-64-character keys with a 400 `ProblemDetail` before touching the database; reset and delete ignore the header                                                                                                                    | Accepted: no fix needed. The check exists because of the `VARCHAR(64)` column, so keep them in step               |
| 14  | Dependencies and the Jib image                    | T      | Known CVEs in libraries or the base image go unnoticed                                                                                                                                                                                                     | Nothing in CI                                                                                                                                                                                                                                                                      | S5: Dependabot, Trivy scan of the image, CodeQL                                                                   |
| 15  | API pod                                           | E      | If the app is compromised, the container has more privileges than it needs                                                                                                                                                                                 | Jib runs as user 1000; `securityContext` is still the commented-out scaffold                                                                                                                                                                                                       | S6: `runAsNonRoot`, `readOnlyRootFilesystem`, drop all capabilities                                               |
| 16  | Any endpoint that uses the database               | D      | With the database down, each request holds a Tomcat thread for 30 seconds (Hikari's default `connection-timeout`) before failing; a few hundred requests would tie up the default 200-thread pool                                                          | Nothing                                                                                                                                                                                                                                                                            | Decide: a shorter `spring.datasource.hikari.connection-timeout`, and/or a client-side request timeout             |
| 17  | API pod readiness probe                           | D      | The pod stays Ready with no database, so Kubernetes keeps routing traffic to a pod that can only return 500s. Making readiness depend on the database has its own cost: a database outage then removes every pod and clients get connection errors instead | Nothing                                                                                                                                                                                                                                                                            | S6: decide whether readiness should include the database                                                          |

## Evidence

- Row 5: checked in jshell first: `0 + 2147483647` → `2147483647`, `+ 2147483647` → `-2`; `Math.addExact` throws `ArithmeticException: integer overflow`. Then reproduced against the API by the red-first integration test `incrementPastMaxIntReturns422AndKeepsCount`: a counter created with `start: 10`, `step: 2147483647` returned 200 with `count: -2147483639` on its first increment. After the fix the same test is green: the increment returns 422 `application/problem+json` and a `GET` shows the count is still 10.
- Row 4: two "Sevens" counters were created on 2026-10-08 with `Idempotency-Key`s, then deleted in the UI. Sending one of those keys again still returned the stored `201` and the deleted counter's body (`Idempotent-Replayed: true`; MariaDB logged `Duplicate entry … for key 'PRIMARY'` for each replay). This is correct idempotency behaviour, but the stored body outlives the counter, so in S3 a replay must only go to the user who created the key.
- Row 6: those two counters disappeared, and nothing recorded it. The `counter` rows are gone, the `idempotency_key` table still shows them being created, and the API logs show no requests at all. We only knew they had been deleted in the UI because the person who did it said so.
- Row 11: probed on 2026-10-08. `/actuator` lists only `health`; `/actuator/env`, `/actuator/heapdump` and `/actuator/beans` return 404; `/actuator/health` returns `{"groups":["liveness","readiness"],"status":"UP"}`. The startup log says "Exposing 1 endpoint beneath base path '/actuator'".
- Rows 10 and 11, after the fix: checked against the cluster on 2026-10-08. The startup log says `The following 1 profile is active: "prod"`; `/v3/api-docs` and `/swagger-ui/index.html` return 404, while `/actuator/health` and `/api/counters` still return 200. `OpenApiSpecTests` still passes (tests run without the `prod` profile), and End to End Tests passed in CI with the chart's `prod` default.
- Row 13: probed on 2026-10-08. `IdempotencyAspect` rejects keys that are blank or longer than 64 characters before touching the database: a 65-character key on `POST /api/counters` returned 400 `{"detail":"Idempotency-Key must be 1 to 64 characters", …}`. A 58-character key (a UUID plus 22 characters) was accepted, as expected. Reset and delete aren't `@Idempotent` and ignore the header (a 65-character key on reset returned 200).
- Rows 7, 16 and 17: probed on 2026-10-08 with MariaDB scaled to 0 replicas. `GET /api/counters` hung for 30 seconds, then returned `500` with `Content-Type: application/json` and `{"timestamp":"2026-10-08T19:46:08.507Z","status":500,"error":"Internal Server Error","path":"/api/counters"}`: no exception message, but not a `ProblemDetail` either. The UI showed "Loading counters…" for those 30 seconds. The API pod stayed `1/1 Running` (Ready) throughout.
- Row 7, after the fix: the red-first slice test first threw `ServletException: Request processing failed: java.lang.RuntimeException: secret detail` (nothing handled the exception), then failed with `"detail":"secret detail"` in the body when the first handler returned `ex.getMessage()`, then passed with the fixed detail. Repeating the database-down probe against the cluster on 2026-10-08: after the same 30-second wait the UI showed "Couldn't load counters: An unexpected error occurred", and the API log recorded `ERROR … ApiExceptionHandler : Unhandled exception` with `CannotCreateTransactionException: Could not open JPA EntityManager for transaction` and its stack trace.
- Other bad input already gives 400 `ProblemDetail`s: a non-UUID id (`"Failed to convert 'id' with value: 'abc'"`) and malformed JSON (`"Failed to read request"`).
